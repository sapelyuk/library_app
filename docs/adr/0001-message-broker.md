# ADR-0001. Выбор брокера сообщений

- **Статус:** принято
- **Дата:** 2026-10-01
- **Задача:** #7
- **Реализация:** вынесена в #14 (`pkg/events` + продюсеры/консьюмеры)

## Контекст

Сервисам нужен асинхронный обмен доменными событиями: `book.borrowed`,
`loan.overdue`, а также уведомления между сервисами (например, book-service
уведомляется о новой сессии user-service). Часть событий требует **отложенной
доставки** — напоминания о сроке возврата и TTL-сессии должны приходить в
будущем, а не сразу.

Синхронное взаимодействие уже идёт через gRPC; брокер закрывает только
асинхронную часть, чтобы сервисы не были связаны прямыми вызовами и переживали
кратковременную недоступность потребителя.

## Рассмотренные варианты

- Apache Kafka
- RabbitMQ
- NATS (+ JetStream)

## Критерии выбора

1. Простота интеграции с Go.
2. Требования к инфраструктуре.
3. Гарантии доставки.
4. Отложенные сообщения (для TTL-сессий).

## Решение

**RabbitMQ** (образ `rabbitmq:4-management`).

## Обоснование

| Критерий | Kafka | RabbitMQ | NATS/JetStream |
| --- | --- | --- | --- |
| Интеграция с Go | `franz-go`/`kafka-go`, много boilerplate | **`amqp091-go`** (официальный), лаконично | `nats.go`, лаконично |
| Инфраструктура | JVM, ~1 ГБ, тюнинг топиков | один контейнер, ~150–250 МБ | **бинарник, ~10 МБ** |
| Гарантии доставки | at-least-once, реплей лога | at-least-once (publisher confirms + ручной ack) | at-least-once через JetStream |
| Отложенные сообщения | **нет** — нужен свой scheduler | **есть**: TTL + dead-letter exchange | нет из коробки |

Критерий 4 оказался решающим: отложенная доставка прямо заявлена в требованиях
(TTL-сессии, напоминания о due-date). В RabbitMQ это штатный механизм
(TTL + DLX либо плагин `rabbitmq_delayed_message_exchange`), тогда как в Kafka
такое пришлось бы эмулировать отдельным сервисом-планировщиком. Гибкая
маршрутизация через topic exchange (`loan.*`, `book.*`) и management UI для
отладки — дополнительные плюсы не в ущерб простоте.

Kafka избыточна для объёма событий библиотеки (нет задачи на replay/event
sourcing). NATS лёгкий, но отложенную доставку тоже пришлось бы строить вручную,
а экосистема для отладки скромнее.

## Модель событий

- **Exchange:** один topic exchange `library.events` на все доменные события.
- **Routing key** = тип события в формате `<aggregate>.<action>`:
  `book.borrowed`, `book.returned`, `loan.overdue`, `user.session.created`.
- **Queue потребителя** привязывается к exchange набором binding-ключей
  (поддерживаются wildcards `loan.*`).
- **Конверт сообщения** (JSON в теле, метаданные в AMQP headers):

  ```json
  {
    "event_id": "uuid v4",
    "event_type": "book.borrowed",
    "occurred_at": "RFC3339 UTC",
    "payload": { "...": "поле специфично для типа события" }
  }
  ```

- **Гарантии:** publisher confirms на стороне продюсера, ручной `ack` после
  обработки на стороне консьюмера, `delivery-mode=2` (persistent).
- **Отложенная доставка:** сообщение публикуется в очередь с `x-message-ttl`
  и `x-dead-letter-exchange`; по истечении TTL оно попадает в очередь
  потребителя. Для напоминаний о due-date TTL вычисляется как
  `due_date - reminder_lead_time`.

## Последствия

**Положительные:**
- Штатная отложенная доставка без отдельного scheduler-сервиса.
- Лёгочная локальная инфраструктура: `docker compose up rabbitmq`.
- Management UI (`:15672`) для отладки bindings и очередей.

**Отрицательные / ограничения:**
- Нет реплея истории: сообщение удаляется после ack (для этого нужны Kafka
  или RabbitMQ Streams — не требуется в текущем объёме).
- Порядок гарантирован только в пределах одной очереди.
- Двойная запись: брокер не заменяет PostgreSQL-состояние сервиса; согласованность
  между сервисами достигается событиями, а не общей БД.

**Не снимается выбором брокера:** решение инкапсулируется за брокер-агностичным
интерфейсом `Publisher`/`Subscriber` в `pkg/events` (#14), чтобы смена брокера
не затрагивала бизнес-логику сервисов.
