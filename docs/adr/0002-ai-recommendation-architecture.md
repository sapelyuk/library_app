# ADR-0002. Архитектура AI-сервиса рекомендаций книг

- **Статус:** принято
- **Дата:** 2026-10-02
- **Задача:** #21

## Контекст

Прототип agentic RAG-системы рекомендаций книг собран отдельно:
[n8n workflow](https://github.com/n8n-io/n8n) + Postgres/pgvector + Gemini embeddings + Gemini/LLM.
Система работает от начала до конца: 20 книг проиндексировано, обе точки входа (чат и HTTP webhook)
прошли дымовой тест.

Теперь нужно интегрировать RAG в монорепо `smart-library` в рамках архитектуры микросервисов:
- Каждый сервис — отдельный Go-модуль с gRPC-контрактом, изолированной БД и REST-слоем.
- `Book Service` — источник истины для каталога книг.
- Взаимодействие между сервисами — gRPC и асинхронные события через RabbitMQ (ADR-0001).

Прототип использует n8n (low-code), что удобно для прототипирования, но не вписывается в
правила проекта: нет gRPC/proto, нет аутентификации, нет изоляции данных.

## Рассмотренные варианты

### Вариант A — n8n как чёрный ящик (прямое использование)

Обернуть n8n в Docker, expose webhook `/recommend` как REST-API.
Фронтенд/gateway вызывает его напрямую.

### Вариант B — тонкий Go-адаптер `ai-service` (выбран)

Новый Go-модуль `services/ai-service/` с gRPC-контрактом `ai.v1.AiService`.
n8n остаётся внутренней реализацией внутри этого модуля.
Внешние клиенты (gateway, фронтенд) не знают про n8n.

### Вариант C — нативный Go-порт RAG (отложенный)

Полностью переписать RAG-цикл (retrieval, embedding, LLM, tools) на Go без n8n.

## Критерии сравнения

| Критерий | Вариант A (чёрный ящик) | Вариант B (Go-адаптер) | Вариант C (нативный Go) |
| --- | --- | --- | --- |
| Встраивание в монорепо | ❌ ломает контракты, нет auth | ✅ единый стиль, gRPC/proto | ✅ единый стиль, gRPC/proto |
| Скорость внедрения | ⚡️ сразу | 🕐 1–2 недели | 🕐 2–4 недели |
| Контроль над инфраструктурой | ❌ n8n вне контроля проекта | ✅ n8n скрыт за интерфейсом | ✅ полный контроль |
| Поддержка RBAC/gateway | ❌ webhook без auth | ✅ через interceptor | ✅ через interceptor |
| Альтернативная реализация | ❌ клиент привязан к n8n | ✅ интерфейс позволяет замену | ✅ Go-код |
| Зависимость от внешних решений | ❌ да (n8n) | ✅ минимальная (внутренняя) | ❌ нет |

## Решение

**Вариант B — принят.**

Создаётся новый Go-модуль `services/ai-service/`:

- **Контракт** `ai.v1.AiService` (proto + grpc-gateway):
  - `Recommend(query, user_context) → [Book]` — рекомендация по запросу.
  - `IngestBook(book_id) → success` — принудительная переиндексация книги.
- **Внутренняя реализация** — HTTP-клиент к n8n webhook'ам (инкапсуляция в `internal/adapters/n8n/`).
- **Синхронизация каталога** через RabbitMQ (ADR-0001): Book Service публикует
  `book.created/updated/deleted`, ai-service потребляет и вызывает ingest/delete.
- **Аутентификация** — через gRPC-интерцептор (тот же pattern, что в user-service).
- Артефакты прототипа (n8n workflow, schema, скрипты) перенесены в
  `services/ai-service/rag/`.

Вариант C рассматривается как естественное направление развития:
когда n8n упрётся в квоты бесплатных тарифов или production-требования,
агентский цикл (tools, memory, retry) переписывается на Go.
Контракт `ai.v1.AiService` не изменится — замена реализации локальна.

## Последствия

### Положительные
- Единый стиль проекта: каждый сервис — Go-модуль с gRPC/proto и Swagger.
- n8n можно заменить без изменения контракта и клиентов.
- Каталог синхронизируется автоматически через события (источник истины — Book Service).
- Артефакты прототипа версионируются в репозитории (`services/ai-service/rag/`).

### Отрицательные / риски
- n8n остаётся зависимостью — требует отдельного контейнера, управления ключами API.
- Двойная запись каталога: Book Service → события → ai-service → pgvector.
- Квоты бесплатных тарифов Gemini ограничивают объём рекомендаций; документирован fallback на Groq.
