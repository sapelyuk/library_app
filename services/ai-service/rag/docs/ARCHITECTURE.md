# ARCHITECTURE — Book Recommender RAG System

> Сопутствующие документы: [RULES.md](RULES.md) (ограничения), [DECISIONS.md](DECISIONS.md) (почему),
> [SETUP.md](SETUP.md) (запуск), [PROGRESS.md](PROGRESS.md) (состояние).

## 1. Назначение

Дать пользователям библиотеки персональные рекомендации книг, опирающиеся **только** на её реальный
каталог, и предоставить эту возможность и через чат-интерфейс, и через HTTP API.

Два видимых пользователю поведения, и оба обслуживает один агент:

| Поведение | Пример запроса | Механизм |
|---|---|---|
| **Рекомендовать** | «Мне очень понравилась *Dune* — что ещё мне может понравиться?» | Векторный поиск по проиндексированному тексту книг, затем рассуждение LLM по найденным кандидатам |
| **Просмотр / поиск** | «Какая у вас есть научная фантастика?», «Расскажи мне о книге 42» | Параметризованные инструменты метаданных |

## 3. Модель данных

Две таблицы. Содержимое и метаданные **разделены**, чтобы метаданные можно было дёшево запрашивать и
фильтровать, не касаясь векторов, и чтобы повторное разбиение книги на чанки никогда не теряло её
запись в каталоге.

### `books` — одна строка на книгу (каталог)

| Колонка | Тип | Примечания |
|---|---|---|
| `book_id` | `text` PK | Стабильный слаг или ID источника (например, ISBN). Ключ идемпотентности. |
| `title` | `text` NOT NULL | |
| `author` | `text` | |
| `genre` | `text` | Основной жанр; используется для фильтрации в `list_library` |
| `tags` | `text[]` | Свободные темы, например `{space-opera,politics}` |
| `published_year` | `int` | |
| `page_count` | `int` | |
| `language` | `text` | |
| `rating` | `numeric(3,2)` | |
| `description` | `text` | Аннотация — активно используется при обосновании рекомендаций |
| `content_hash` | `text` | Хеш проиндексированного исходного текста; позволяет загрузке пропускать неизменившиеся книги |
| `source` | `text` | Откуда пришло: `webhook`, `bulk`, `csv` |
| `created_at` / `updated_at` | `timestamptz` | |

### `book_chunks` — одна строка на каждый эмбеддированный чанк

| Колонка | Тип | Примечания |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()`, именно та колонка, в которую пишет n8n |
| `book_id` | `text` NULL | **Внешнего ключа нет, намеренно** — см. ниже |
| `chunk_index` | `int` NULL | Зарезервировано; загрузчик n8n сейчас его не передаёт |
| `text` | `text` | Текст чанка, который был эмбеддирован (имя колонки, которое ожидает n8n) |
| `metadata` | `jsonb` NOT NULL DEFAULT `'{}'` | Содержит `book_id`, `title`, `author`, `genre` |
| `embedding` | **`halfvec(3072)`** | **EMBEDDING_DIM зафиксирован — ADR-002, ADR-005b** |

**Почему `book_id` допускает NULL и не имеет внешнего ключа:** узел insert векторного хранилища
PGVector в n8n записывает только `id`, `text`, `metadata`, `embedding`. Он никогда не передаёт
`book_id`, поэтому ограничение NOT NULL или внешний ключ провалили бы каждый insert. Авторитетной
связью поэтому является **`metadata->>'book_id'`**, и именно так она читается везде. Удаление книги
идёт через `delete_book(book_id)`, который удаляет строку каталога и её чанки вместе — база данных не
может выполнить каскад за нас. Проверено на живом контейнере: первая версия схемы с `NOT NULL` + FK
провалилась бы при каждой загрузке.

**Почему `halfvec`, а не `vector`:** pgvector не может построить HNSW-индекс по обычной колонке
`vector` размерностью выше 2000, а эта колонка — 3072. `halfvec` поддерживает до 4000 измерений и
хранит 2 байта на измерение вместо 4, вдвое сокращая объём хранения примерно до 6 КБ на чанк.
`EXPLAIN` подтверждает, что индекс используется. Полную историю см. в ADR-005b — это был реальный
сбой, а не предпочтение.

Уникальные ограничения здесь тоже не могут обеспечить идемпотентность, потому что n8n генерирует
новый uuid при каждом insert. Поэтому идемпотентность повторной индексации **явная**: workflow
выполняет параметризованный `DELETE FROM book_chunks WHERE metadata->>'book_id' = $1` перед повторной
вставкой.

### Функции SQL (параметризованные — агент никогда не пишет SQL)

| Функция | Сигнатура | Возвращает |
|---|---|---|
| `match_book_chunks` | `(query_embedding halfvec(3072), match_count int DEFAULT 8, filter_genre text DEFAULT NULL, filter_book_id text DEFAULT NULL)` | `book_id, title, author, genre, chunk_text, similarity` — упорядочено по косинусному сходству |
| `get_book` | `(p_book_id text)` | полную строку метаданных для одной книги |
| `list_books` | `(search_query text DEFAULT NULL, limit_n int DEFAULT 25, offset_n int DEFAULT 0)` | строки каталога; один терм нечёткого совпадения по title/author/genre/tags/description |
| `delete_book` | `(p_book_id text)` | `deleted_chunks, deleted_book` — атомарно удаляет строку каталога **и** чанки |

> `list_books` намеренно принимает **один** аргумент: модель, передающая несколько аргументов
> `$fromAI` в гарантированном порядке, ненадёжна, поэтому отдельные фильтры по жанру и автору были
> сведены в один терм.
>
> Роли `bookrag_readonly` выданы `SELECT` на обе таблицы и `EXECUTE` на три читающие функции — но
> **не** на `delete_book`.

## 4. Поток загрузки (подробно)

1. **Триггер** — либо ручной/массовый триггер (читает `samples/books.csv` или glob по папке), либо
   `Webhook` загрузки для одной книги.
2. **Flatten Book Fields** — поглощает обёртку `body` от webhook и нормализует путь к CSV, чтобы
   нижестоящим узлам никогда не нужно было знать, какая точка входа сработала.
3. **Prepare Book Record** (Code) — выводит `book_id` (слагифицированный `author-title`, либо
   собственный id вызывающей стороны), строит индексируемый `text` (title + author + genre +
   description + content), нормализует типы и превращает строку `tags` в настоящий массив.
4. **Loop Over Books** — размер пакета 3, чтобы оставаться в пределах лимитов запросов бесплатного
   тарифа.
5. **Delete Previous Chunks** — параметризованный `DELETE ... WHERE metadata->>'book_id' = $1`, шаг
   идемпотентности (см. примечания к таблице выше).
6. **Recursive Character Text Splitter** — размер чанка 1000, перекрытие 200.
7. **Book Document Loader** — `jsonMode: expressionData` загружает `{{ $json.text }}`, ключи
   метаданных записаны **без** ведущего `=`: `book_id`, `title`, `author`, `genre`. `textSplittingMode`
   **должен** быть `custom`, иначе подключённый splitter молча игнорируется.
8. **Postgres PGVector Store (insert)** — таблица `book_chunks`, эмбеддинг предоставляется
   единственным узлом эмбеддингов Gemini.
9. **Upsert Book Metadata** — параметризованный `INSERT … ON CONFLICT (book_id) DO UPDATE` в `books`
   (11 параметров).
10. Цикл повторяется, пока не будут обработаны все элементы.

**Семантика сбоев:** узлы извлечения и эмбеддингов несут `onError: continueRegularOutput` плюс
повторы, а upsert метаданных происходит **после** сохранения содержимого. Поэтому сбой оставляет
книгу отсутствующей в индексе (восстановимо повторным запуском), а не оставляет каталог заявляющим о
книге, у которой нет доступного для поиска содержимого. Шага «сначала удалить» нет нигде.

## 5. Поток запроса (подробно)

1. **Триггер** — триггер чата (`When chat message received`) или `Webhook` рекомендаций.
2. **Normalise Chat Input** — формирует `chatInput` и `sessionId`. Тело webhook использует
   `{ "chatInput": "...", "sessionId": "..." }`; триггер чата предоставляет и то и другое изначально.
3. **Book Recommendation Agent** — агент, вызывающий инструменты. Системный промпт требует: искать
   перед ответом, рекомендовать только книги, возвращённые инструментами, объяснять, *почему* каждая
   подходит пользователю, никогда не выдумывать название и прямо говорить, когда в библиотеке нет
   ничего подходящего.
4. Доступные инструменты:
   - `Search Book Library` — основной RAG-инструмент; режим `retrieve-as-tool` по той же таблице
     векторов. Принимает строку запроса. *(При PGVector typeVersion ≥ 1.3 имя инструмента, которое
     видит модель, — это **имя узла**, поэтому переименование узла переименовывает инструмент —
     держите системное сообщение синхронизированным.)*
   - `Get Book Details` — точный поиск по `book_id` через параметризованный `get_book($1)`.
   - `List Library` — просмотр/поиск по одному свободнотекстовому терму через `list_books($1, 25, 0)`.
   - `Remove Book` — единственный изменяющий инструмент; `delete_book($1)`. Отключите узел, если агент
     не должен иметь возможности что-либо удалять.
5. **Postgres Chat Memory** — хранит многоходовой контекст с ключом по `sessionId`, поэтому уточнения
   вроде «а есть что-нибудь покороче?» работают без повторного изложения запроса.
6. **Respond to Webhook** — возвращает ответ агента как JSON на API-пути.

## 6. Стратегия рекомендаций

Обычный векторный поиск отвечает на вопрос «какой текст похож на этот текст», а это *не* тот же самый
вопрос, что «что этому человеку понравится». Три механизма закрывают этот разрыв:

1. **Расширение запроса агентом.** Системный промпт предписывает агенту превращать высказывание о
   вкусе («мне понравилась Dune») в описательный поисковый запрос (темы, темп, тон, предмет), а не
   искать только буквальное название.
2. **Сначала кандидаты, потом рассуждение.** Агент извлекает набор кандидатов (по умолчанию 8 чанков),
   затем рассуждает по `description` + совпавшему содержимому, чтобы выбрать и обосновать короткий
   список — обычно 3 книги с одной строкой *почему* по каждой.
3. **Уточнение с учётом памяти.** Поскольку история сохраняется по каждому `sessionId`, агент может
   рассматривать разговор как текущий профиль вкусов, а не отвечать на каждое сообщение изолированно.

## 7. Известные ограничения (будьте честны с пользователем)

- Поиск на уровне чанков может терять контекст всей книги; `get_book_details` существует отчасти
  чтобы его восстановить.
- Лимиты запросов бесплатного тарифа ограничивают, как быстро можно проиндексировать большую
  библиотеку.
- Рекомендации хороши ровно настолько, насколько хороши `description`/содержимое в каталоге. Каталог
  только с названиями (без аннотаций) даст слабые рекомендации — исправление в лучших данных, а не в
  лучшем коде.
- Нет модели пользовательских учётных записей: `sessionId` предоставляет вызывающая сторона, поэтому
  вызывающий может прочитать историю другой сессии, если угадает ID. Приемлемо для использования на
  localhost; вернуться к этому до публичного раскрытия.

## 8. Будущие расширения (задокументировано, не реализовано)

- Триггер папки Google Drive как третий путь загрузки (требует пользовательский OAuth).
- Индекс HNSW вместо ivfflat для больших библиотек.
- Цикл обратной связи `rate_book`, записывающий оценки пользователей обратно в `books.rating`, чтобы
  смещать рекомендации.
- Таблица истории рекомендаций по пользователям для профилей вкусов между сессиями.
